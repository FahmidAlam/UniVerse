## Repeatable local verification



Requires Python 3.11+, Docker Desktop's Linux engine (or Linux Docker), and

Supabase CLI **2.121.0**. The CLI help/version, init, migration new, start,

db reset and test db commands were inspected for this version. The local CLI

binary was downloaded to a temporary task directory and SHA256-verified against

the official release manifest; PATH was not changed.



Run from the repository root:



```powershell

python tool/task1_local_checks.py

```



If the CLI is not on PATH, pass its executable path with `--cli`.

The verifier accepts no hosted URL, project reference, password or access token.

It checks the Docker endpoint is local, creates a new owned temporary directory

and unique local project identifier, and refuses linked or unowned directories.

Only that generated local project is reset. It never links, pushes or deploys.



The CLI-named review artifact is

[20261021214512_reconstructed_baseline.sql](../supabase/reconciliation/20261021214512_reconstructed_baseline.sql).

It stays outside the historical migrations directory and matches the generator.

The verifier creates a fresh CLI-named migration from reconstructed stages 001-004,

then performs **two fresh local resets** in the real public namespace. Each pass:



1. Runs rollback-only role, ownership, escalation and publication checks.

2. Creates the four empty local buckets through the local Storage API and applies

   the supplied legacy Storage policy baseline while Auth is empty.

3. Runs exact catalog checks and the original pgTAP application contract suite.

4. Restores the actual 795-row/four-version sanitized fixture into public tables,

   compares every restored field/count/checksum, rolls back, and checks emptiness.

5. Reports PostgreSQL and extension versions. The local stack is stopped on exit;

   its temporary files/volumes are retained for diagnosis, never silently deleted.



The root [config.toml](../supabase/config.toml) is a local template generated by

`supabase init`. Automatic migrations and seeds are **disabled** there because

historical migrations are not a valid fresh-install chain. The verifier enables

only its separately generated reconstructed baseline. Do not run old migrations

or use `db reset --linked`, migration repair, or a production schema pull as a

substitute. Existing migration filenames and remote history are unchanged.



[validate.yml](../.github/workflows/validate.yml) runs the Python safety tests,

Deno authorization/audience tests, and the same two-pass local verifier on an

isolated GitHub runner, with no repository secrets or hosted credentials. Adding

this file does not mean GitHub Actions has already executed it.



Verified runtime: Supabase CLI 2.121.0, Docker server 29.9.2, PostgreSQL 17.11

(`supabase/postgres:17.11.0.004`), vector 0.8.2, pgTAP 1.3.3 and Deno 2.5.6.

The reviewed Docker guard pins the checked local socket and removes inherited

context overrides, so a conflicting remote context cannot override the target.



## Deliberate differences and deployment limits



- The source reports vector 0.8.0; the observed hosted test has vector 0.8.2.

  Local reconstruction explicitly requires 0.8.2 and fails on other versions.

  No extension downgrade or silent drift acceptance is performed.

- Client grants reproduce SELECT/INSERT/UPDATE/DELETE, deliberately omitting

  legacy TRUNCATE/REFERENCES/TRIGGER. Preserved broad legacy policies are evidence

  of existing behavior, not approval for production use.

- Applied source migration history is absent/unavailable. The reconstructed

  baseline is not represented as a recovered dump or applied source migration.

- All 17 Dart table constants are covered by the catalog. The two bucket

  constants referenced by current Dart callers (`resources`, `timetables`)

  match the recovered buckets. The unused `bucketSubmissions = 'submissions'`

  declaration does not match the deployed `assignments` bucket; this drift is

  recorded without creating a new bucket or changing unrelated client code.

- The backup contains current routine fields and limited version metadata.

  Teacher/publisher identity foreign keys restore as null; Auth accounts, bucket

  files, secrets, timetable input catalogs/settings and deleted historical rows

  are outside this backup. Full production disaster recovery is not certified.

- Existing test Auth users stay intact. No real invitations, FCM credentials,

  notification webhook or production secret configuration is created by this work.

- The current send-push entry point needs `index.ts`, `webhook_auth.js` and

  `audience.js`. Its dedicated secret is `PUSH_WEBHOOK_SECRET`; the caller must

  supply the identical private value in `x-webhook-secret`. Hosted test endpoints

  deliberately reach the handler gate with gateway JWT verification disabled.

  Do not change production settings or deploy without a reviewed rollout.

- Full notification delivery, positive invitation/email behavior, live Realtime,

  and remediation of broad legacy Storage grants remain integration/rollout work.



Reference: [Supabase local development workflow](https://supabase.com/docs/guides/local-development/cli-workflows).

Never share passwords, API keys, access tokens or private webhook header values.


## Task 2 catalog implementation and approval boundary (22 October 2026)

The additive catalog implementation is available locally in
`supabase/migrations/20261022140809_academic_catalog.sql`. It is not deployed to
any hosted project. Root automatic migration replay remains disabled because
historical migration files have not been approved as a provisioning chain.

Run the isolated verifier with:

```powershell
python tool/task1_local_checks.py --task2 --cli <path-to-Supabase-2.121.0>
```

It creates its own disposable local Docker project, reconstructs the accepted
Task 1 baseline, restores the sanitized 795 routines/four versions, applies the
catalog migration and compares every legacy routine field before and after.
It runs scoped RLS, identity, alias and reviewed-mapping tests, and parses a
program-scoped SQL catalog snapshot through the strict Python model. The
process repeats after a fresh local rebuild and stops only its owned stack.
No hosted project credentials are needed. The GitHub validation workflow uses
this same command with `--task2`.

Catalog writes go through `AcademicConfigService`; reads use one atomic
`academic_catalog()` RPC. Program/department memberships are database authority;
client profile labels do not grant capabilities. Alias saves replace their
atomic group membership transactionally and invalidate prior review. Separate
approval capability is required to review an alias. Nullable profile/routine
references preserve old IDs, roles, labels and legacy payloads. Generation and
publication still use their existing adapters; these catalog APIs do not enable
multi-department publication.

**Actual CSE identity backfill has not been performed.** Formal calendar/term
rollout is deferred; the audit/plan clarification override supersedes the earlier
calendar approval prerequisite for parser work. The read-only assessment in
`docs/timetable-audit-2026-10-20/task2-backfill-status.json` holds all 795 fixture
rows for review and proposes/applies zero identity links. Of these, 125 have an
end time at or before their start time. This flags stored time anomalies, not
invalid source classes; a parser defect is reproduced in the corrected audit.
Current study stages and real teacher identities cannot be inferred from this
sanitized fixture. B+C joint attendance is now confirmed; each occurrence still
needs its authoritative source-cell link. Summer/winter timing applicability
must be verified separately; formal calendar rollout is deferred. This is a
quarantine report, not a hosted quarantine write.

The SQL mapping path accepts stored, approved batches and checks the complete
original row before adding canonical links. It refuses stale source rows,
unreviewed aliases, mismatched study stages, unresolved nonblank teachers,
unknown rooms and invalid same-day intervals. Synthetic tests cover atomic
combined-group links, exact legacy-field preservation and idempotent reapplication.
Actual identity mapping acceptance still needs reviewed source identities and
source/as-of stage/alias evidence. Calendar-specific Task 2 integration is
deferred; no fabricated term is needed to finish the present audit.
