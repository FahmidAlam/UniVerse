## Confirmed decisions and historical corrections

The following decisions are confirmed; do not ask them again. Current support ratings still describe existing code, not the approved future behavior.

| Decision | Confirmed user/committee policy | Initial audit interpretation superseded | Existing implementation and future implication |
|---|---|---|---|
| **D1 — Independent section weekends; R1/R2** | Each section may have its own consecutive two-day weekend, using an applicable default with an optional section-level UI override. Never force identical weekend identities across a batch. Preserve maximum difference **one** in total weekly days off among sections of the same batch. | Whether sections can differ and whether the maximum one-day difference is binding are no longer open questions. | `solver._groups()` reserves all atomic section members of a joint class, but `solve()` has no weekend/fairness constraint. Existing `TimetableSettings.workingDays` is a global teaching grid, and faculty `offDays` belongs to people, so neither is a section weekend store. Reuse shared weekday controls where useful; introduce only missing section-policy applicability/override storage after inspecting catalog groups/scopes. Validate pair per section and batch max–min off-day count ≤1. |
| **D2 — Theory policy; R13** | CSE theory at **1, 1.5 or 2 credits** has exactly **two weekly classes**, both in one day, consecutive slots, same classroom. Three-credit CSE theory is distributed across the section's working days, not forced into that block. Its count and precise spread must not be guessed. UI must support validated course policies. | One-credit meeting count is settled; 1.5 credits is explicitly included. The initial 1/2-credit-only wording is historical. | `ingest.Offering.credit` is carried, but `derive_required_sessions()` uses fixed/total/hint/default, not credits. Default same-day ban, residual same-day penalty for exemptions, `_build_pairs()` sibling theory/lab adjacency and post-placement `_assign_rooms()` all need coordinated changes later. An exemption alone neither enforces a block nor common room. Report conflicts with source totals/old pairing; do not silently override them. |
| **D3 — Permanent faculty attendance; R7** | Normally **two configured off-days**; explicitly configurable **three where necessary**. Corresponding **five/four university attendance days** need not contain teaching periods. Faculty should select off-days through UI under approved policy. Faculty off-days need not be consecutive. Three days off is an option, not an automatic grant. | The initial proposed test “4–5 active teaching days” is incorrect. An empty teaching day does not establish a faculty off-day. | Reuse `TimetableFaculty.offDays` → `TimetableFacultyController.save()` → config `off_days` → `solve.valid_slots()` / `_validate()`. Existing admin faculty editor has day chips but no employment-category/count enforcement, attendance representation or faculty-owned editing authorization. Extend this path rather than create a duplicate weekend manager. Self-service needs verified faculty/profile linkage and an authorized own-record write path, not global admin privileges. |
| **D4 — Adjunct distinct-course counting; R6** | Count distinct assigned courses per faculty, regardless of number of sections. CSE-3101 in A and B is one course; adding CSE-3102 makes two. Keep 2→within 2 days, 3→3–4, 4+→4–5 workload preferences; one-course case and strictness/exactness remain open. | Counting section offerings as courses is rejected; course-count unit is no longer a question. | An ingest offering is keyed by cohort/course, so counting offerings overcounts. Deduplicate reviewed course identities over actual assignments and all known attached faculty. Do not count eligibility rows, sessions, source rows or sections. `Offering.teachers` and pending source rows must survive corrections; split versus co-teaching remains explicit. Proposed canonical course IDs may help later; their current lack of runtime integration is not solved by a code-label heuristic. |
| **D5 — Explicit sessional break permission; R12** | The preferred consecutive same-lab pair for a **2-credit sessional** may span the scheduled break only with explicit admin UI permission. Summary must show permission enabled/disabled. Permission does not apply to every break-related rule. | General break semantics remain separate; the new permission must not be silently enabled or inferred from `break_col`. | `solve()` currently defines neighbors by touching clock endpoints; break-separated teaching slots are nonadjacent. Represent consecutive **teaching-slot** ordering and clock intervals separately. Proposed permission is false until explicitly enabled and frozen with the relevant policy/pattern revision. When permission is enabled a pair can be on either side of break, with same physical lab and all hard availability rules satisfied. Pair preference remains soft, exact three weekly classes remains mandatory. Do not globally change theory adjacency, section gaps or SUST break preference. |
| **D6 — Mandatory conflicts and outcomes; all rules** | Never silently weaken mandatory requirements. Identify affected rules/resources/intervals, explain the conflict and configuration needing attention, allow authorized traceable correction, then validate/generate again. Distinguish proven infeasibility, timeout/budget exhaustion, unknown result, invalid/incomplete input, allocation failure and network/service failure. | Hard-rule violation to obtain a routine is prohibited, not an open product choice. Failed search is not mathematical impossibility. | Current `solve()` accepts only OPTIMAL/FEASIBLE and passes other statuses to `_infeasible_message()`, which starts “No feasible timetable” and suggests relaxing adjacency. Those diagnostics are **not compliant yet**. Future structured outcomes must preserve raw solver status and known termination reason: UNKNOWN is not automatically timeout; timeout with a feasible incumbent may still yield a candidate requiring full validation. Heuristic conflicts must not be presented as proven minimal unsatisfiable sets. |

These decisions establish separate concepts:

- **Section teaching/working days:** days on which section attendance obligations permit scheduling; derive actual section class-free days against the approved week and joint-group membership for R1/R2. Exact treatment of ancillary obligations still needs evidence.
- **Faculty attendance days:** approved university attendance obligations; their complement is configured off-days. Permanent policy uses these, never a count of scheduled classes.
- **Faculty teaching days:** days containing teaching assignments, used for adjunct workload/travel reporting as applicable. A faculty member may attend without teaching.
- **Hard availability:** a person/room's permitted windows after external reservations. Attendance alone does not promise all-day teaching availability; an external appointment may block slots on an attendance day.

An optional section override changes a section policy, not a faculty's off-days. Applying a default does not grant permission to invent a default pair or automatically choose three permanent off-days. The UI must expose resolved values and their provenance.

## Additional required capability — editable Course Distribution

This is an **additional user requirement**, referenced as **CD1**, not a replacement or renumbering of R1–R16. It is not implemented. `generate_timetable_screen.dart` picks a distribution and shows result/report; `TimetableGenController.selectDistribution()` stores bytes and `generate()` submits them. Course eligibility screens edit qualifications, not imported distribution records. `draftMap()` is a generated-routine snapshot, not an editable distribution draft. No editable distribution route/page/store was found.

Formula evidence: Summer J/L contain 308/338 formula cells; Fall J/L contain 455/487. Runtime opens the workbook with `data_only=True`; cached values are consumed and openpyxl does not calculate the formulas. A credit/count edit must therefore not imply Excel recalculation. Retain formula text, original cached value and explicit correction separately, and flag unresolved dependent values. There is no authorized Excel/macro execution or source workbook rewrite.

Derived/read-only fields: `cohort`, `oid`, `sid`, `required_sessions`, `sessions_basis`, `occurrence`, teacher arrays, source-row links and sessions. Recompute from accepted source corrections, retaining stable draft-record identity independently of ephemeral IDs. `is_lab` currently derives from code parity; an explicit course-type/lab-requirement override needs an approved adapter contract. `is_service` derives from batch/section; the optional supported `Is Service` column is absent from both inspected sources. Do not pretend it was supplied or invent unrestricted lab/classification editing. Proposed explicit course-pattern/Physics-code policies remain separate validated configuration.

`ingest_workbook()` groups `(cohort, course code)`, sums class totals, preserves attached teachers in source order and records blank-teacher portions as pending. It warns on credit disagreements while keeping the first known credit; title/dept/headcount/weekly hint effectively retain first-row values. A future editor must surface conflicting merged rows instead of silently inheriting permissive first-row behavior. A source-row view with an offering preview is the smallest practical starting point; directly editing an aggregated offering without allocating split-teacher totals risks changing the academic requirement.

### Proposed minimum draft and generation contract

Keep original uploaded bytes immutable. Maintain **one accepted versioned distribution draft** comprising original record references and validated corrections; use that exact effective revision as the only scheduling input. Original evidence and correction history are provenance, not two competing current authorities.

Proposed required semantics (names are design descriptions, not new tables/API fields): source checksum/sheet/row/column; stable draft record; parent/current revision; correction actor, reason and timestamp; original formula/cache/value; accepted effective value; input/config/resource revisions and validation state. Use revision checks to prevent stale overwrites. Record grouped identity changes and source omissions explicitly. Store originals/corrections under authorized scope, not in public logs.

Future flow: original XLSX → source-record staging → validated corrections → deterministic normalization of the accepted draft → generation + independent validation → preview/export/publication bound to that same revision. Editing a relevant value invalidates existing normalization/output/validation/approval; do not publish a stale result after source correction. Availability/configuration changes likewise require revalidation against their revisions.

The exact integration gap is real: `main._run_job()` currently calls `ingest.ingest_bytes()` and `solver.solve()` on legacy dictionaries; the endpoint accepts file/config/time limit, not a distribution draft. `engine/domain.py` already has `SourceRef`, `TeacherAssignment`, `Offering`, `NormalizedInput`, `PolicySnapshot` and `ValidationReport`, but these records are not integrated into that path. Do not send an unwired DTO or implement duplicate Dart normalization just to make the editor appear to work. Prefer one engine-side normalization boundary with a bounded compatibility adapter while canonical integration is reviewed; the lead must settle that contract before dependent frontend/backend edits. Do not fabricate term dates to satisfy canonical carriers.

| Consumer | Required future consistency |
|---|---|
| Routine configuration | Show draft-effective course/category/credit/count/teacher/group inputs and their policy conflicts. |
| `solver.solve`, `_build_pairs` | Use regenerated meetings and reviewed atomic groups/teachers from the pinned draft; code/credit corrections affect patterns and pair compatibility. |
| `_assign_rooms`, `_validate` | Use the same effective headcount, course owner/type, counts, assignments and source exclusions; check all approved policies independently. |
| `render.render_bytes`, preview | Render the candidate produced from that input; preserve teacher/group identity and separate service rows. Export neither stale source values nor a separate UI-only dataset. |
| `TimetableEngineService`, `publish_routine`, manual/upload paths | Bind validation and publication to the exact accepted draft/config/resource revisions, reject stale/failed input, preserve identities and safe atomic publication. A caller's `ok=true` alone is insufficient. |

## Technical dependencies and safe implementation order

1. **Web/platform foundation first**, owned by Web Architecture and Platform Compatibility. Reuse Flutter/router/services and adapt platform file handling and browser auth; do not require unresolved three-credit policy to finish this milestone.
2. **Course Distribution and configuration design**, owned by Admin UI/UX with Backend/Data Integrity owning revision/authorization contracts and Scheduling owning normalization semantics. Agree the source-record correction contract and grid/pattern rules before parallel writes to consumers.
3. **End-to-end accepted-draft slice** before claiming editable distribution works: persistence/version checks → normalization → UI preview → same-revision generation/validation/export. A table that only changes local displayed values is incomplete. Backend/revision work can be delivered in a narrow subphase of this slice; it need not wait for every future scheduling rule.
4. **Hard policy integration** and shared validation: independent section weekends, batch spread, attendance-aware faculty configuration, availability, course patterns, break permission and room-aware blocks. Resolve legacy same-day/penalty/pairing conflicts explicitly, preserving unaffected regression behavior.
5. **Soft workload/preferences, diagnostics and operational review** after the corresponding semantics are known. Independent Testing/Reliability review checks known-feasible, infeasible, time-limited, stale-draft and unauthorized-edit scenarios. No silent fallback, inferred three-credit count or auto-permission.

No new schema names, SQL, API implementation, additional packages or frontend framework are mandated by this planning document. Formal calendars and multi-department rollout remain deferred; scope-friendly revision keys preserve that future.
