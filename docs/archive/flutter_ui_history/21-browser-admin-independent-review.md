The current user request makes acceptance conditional on no remaining Critical/High defects and sufficient runtime evidence. Web compilation, analysis and all 123 Flutter tests pass, and the actual browser renders the desktop admin screens against synthetic local data. ## Authentication and authorization assessment

Automatic profile provisioning reads the signed-in user identity/email and matching whitelist row, inserts that user's profile and returns it (`AuthService.handlePostLogin`, `auth_service.dart:206–257`). Role selection is not taken from a caller-supplied route or arbitrary user-metadata role. Repository policies restrict profile insertion to the caller ID with admin whitelist requirements; migration `016_teacher_whitelist_gate.sql` adds JWT-email/exact-role checks. The new mocked admin success test does not execute those policies.

No concrete newly introduced unapproved-administrator escalation was found in static review. Ordinary nonwhitelisted users retaining student registration is existing intended behavior. Existing-profile roles are not retroactively revoked by migration 016. None of this certifies the deployed schema/grants: no real Supabase role/REST/RPC negative test was run. Existing broad Storage policies, staff cancellation checks, manual routine writes and caller-supplied publication validation remain documented older boundaries, not fixes delivered by Phase 1 or new findings attributed to this diff.

F1/F2 are inherited functional defects within the broader browser/auth workflows claimed by the handoff; they are not allegations that Antigravity introduced the server invite code or router recovery behavior. F4 is an unverified deployment assumption, not an invented proof of misconfigured hosted URLs. The user acceptance policy requires safe, usable demonstrated authentication; inherited problems cannot be silently excluded when accepting that claim.

## Platform files, generation and mobile assessment

`lib/core/platform/file_downloader.dart` conditionally exports HTML or IO implementations, with a stub that throws `UnsupportedError` otherwise. The web build succeeds. `lib/main.dart` already skips Firebase/push initialization on web. No dependency upgrade or app configuration edit was needed for compilation.

The web adapter creates a Blob, attaches/clicks/removes an anchor and immediately revokes its object URL (`file_downloader_web.dart:11–27,34–44`). Its workbook/JSON MIME types and original bytes/string are supplied directly; there is no identified payload transformation. Immediate URL revocation is a lifecycle point requiring actual download verification, **not a demonstrated failure here**. Native adapter file writes are covered by two IO tests. Native controller paths retain their original directory/opening logic; the abstraction does not replace all native controller behavior, so report 20's “100% preserved” statement is stronger than evidence.

`TimetableGenController.downloadAndOpen()` snapshots privacy/job identity and uses the web downloader only on web (`:244–279`). `saveDraft()` uses JSON download on web (`:297–313`). Private profiles still refuse publication; shared teachers are retained in `allRows`/`toDraftMap()` and the publication guard still refuses lossy hosted co-teacher storage. The existing private-download race safeguard remains. No new loss of these protections was identified by source review or the passing regression suite.

The engine, distribution ingestion, parser, engine service and publication SQL were not changed by this candidate. Upload remains a separate parser/validation path; manual CRUD and the global publish RPC retain their prior limitations. Source preservation is not yet an accepted distribution contract and is not claimed implemented. Full synthetic engine/browser export and physical mobile checks remain unperformed. Existing unit/widget regressions passing supports compatibility but does not establish “full Android/iOS functionality preserved.”

Moving secondary admin pages into `ShellRoute` gives them desktop chrome and hides bottom navigation on mobile secondary routes. Browser back/forward was exercised on dashboard/settings; native hardware-back, mobile sign-in, actual FilePicker/OpenFilex and push behavior were not tested on a device. The existing mobile-oriented `PopScope` behavior deserves a targeted nested-route/device regression rather than an unsupported declaration of full preservation.
